# Delhivery Last-Mile Delay Intelligence Pipeline

Capstone, AI and ML Certification Program, E\&ICT Academy IIT Roorkee. Synthetic data only.


## How to run

From a fresh clone (Python 3.10+):

```bash
git clone https://github.com/<SahillMaqbool>/<delhivery-delay-intelligence>.git
cd <https://github.com/SahillMaqbool/delhivery-delay-intelligence.git>
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\\Scripts\\activate
pip install -r requirements.txt
python generate\_data.py            # prints 24 1224 48
python part\_a\_clean\_eda.py
python part\_b\_regression.py
python part\_c\_classification.py
python part\_d\_segments.py
python package\_model.py            # regenerates models/delay\_model.pkl
python predict\_delay.py            # writes outputs/new\_shipment\_actions.csv
```

`models/delay\_model.pkl` is regenerated by running `python package\_model.py`. The committed pickle loads reliably only on the
scikit-learn version pinned in `requirements.txt`; if your installed versions differ, re-run `package\_model.py` instead of loading it.

## Data findings

Every number below is copied from a file in `outputs/`.

1. **Service type** (`part\_a\_delay\_by\_group.csv`): Service type (part\_a\_delay\_by\_group.csv): Express parcels are delayed most often, with a delay\_rate of 0.4897 (119 of 243 parcels), far above Standard and Economy..
2. **Hub tier** (`part\_a\_delay\_by\_group.csv`): 0.04 -> 0.215 -> 0.44.
3. **Distance band** (`part\_a\_delay\_by\_group.csv`): Distance band: the delay rate climbs sharply with distance, from 0.0219 for lanes up to 200 km to 0.1368 (201-400 km), 0.4364 (401-600 km) and 0.8523 beyond 600 km, where 75 of 88 parcels were late..
4. **Strongest correlations with delivery\_hours** (`part\_a\_correlations.csv`, ranked by absolute value, delivery\_hours excluded): Strongest correlations with delivery\_hours: promised\_hours (0.8372), distance\_km (0.4013) and n\_stops (0.3247).
5. **Why declared\_value\_inr was log-transformed** (`part\_a\_checks.csv`): Log transform: declared\_value\_inr is right-skewed, with a mean of INR 1,533.05 against a median of INR 1,121.50, and taking the natural log pulls them almost together (7.0277 vs 7.0224), so a few expensive parcels no longer dominate the feature.

## Model results (regression)

(from `part\_b\_\*.csv`)

* Baseline R2 on validation = R2 = −0.0212, RMSE = 18.8552 hours. the baseline predicts the training-set average delivery time for every parcel, so it explains none of the variation. The R² is close to 0, and slightly negative because the training average isn’t exactly the validation average. Every real model has to beat it.
* Winner on validation: Linear regression won on validation with an RMSE of 4.8912 hours (R² 0.9313), narrowly ahead of gradient boosting at 4.9165.
* Tree depth: high-bias depths, Depths 1 and 2 are high-bias, with train and validation RMSE both high (11.6334 and 12.1324 at depth 1, a gap of only 0.50). The unlimited tree is high-variance, with train RMSE 0.0 against validation 7.8368. Depth 6 gave the lowest validation RMSE, 6.2796..
* Learning rate: best = 0.1; 0.01 is too slow. With only 100 trees, each tree adds a tiny correction, so the model is still underfit when it stops.; 1.0 overshoots. Each tree applies its full correction, so predictions jump past the target and chase noise.
* Cross-validation vs validation ranking: Cross-validation prefers gradient boosting (mean R² 0.9353 against 0.9261), which disagrees with the validation ranking. The final test score is for linear regression: R² 0.9493, RMSE 4.5235 hours.

## Model results (classification)

(from `part\_c\_\*.csv`)

* Blind baseline accuracy = 0.7667; it is useless because it never flags a delayed parcel (recall 0), ...



* The five noise columns together hold 0.2245 of the forest’s importance, yet all five rank 8th or lower by F-score (each below 5, against at least 36.7281 for the top seven), so the F-test separates signal from noise more cleanly than forest importance does.



* F1 peaks at k = 7 (0.8333), which equals the number of real signal columns: k = 5 drops two real signals (0.6988), and k of 10 or more lets noise columns in (0.7857 to 0.8049).



* Tuning did not beat the untuned forest: the grid scored a validation F1 of 0.7750 and the randomized search 0.7848, against 0.8333 for the default. With only 42 delayed validation parcels, one parcel moves F1 by about 0.02 to 0.03, so these gaps are within noise and 180 rows cannot reliably separate the configurations.



* The alert threshold is 0.5, the highest value with validation recall of at least 0.80 (0.8333, precision 0.7955). At 0.6 recall falls to 0.7619, and at 0.1 recall rises to 0.9762 but precision drops to 0.4824, so 0.5 is the best compromise under the recall rule.



* On the test set the final model scored precision 0.6889, recall 0.7561 and F1 0.7209. Test recall is lower than the validation recall of 0.8333 and under the 0.80 target; with only 41 delayed test parcels one parcel shifts recall by about 0.024, and the threshold was tuned on one validation split, so I would not promise 80% recall in production.



## Operations recommendation

* The Escalate segment holds nine hubs (Guwahati 0.62, Agartala 0.54, Raipur 0.48, Nagpur 0.46, Patna 0.46, Siliguri 0.44, Bhubaneswar 0.40, Ranchi 0.38, Kochi 0.36) with a segment delay rate of 0.46, against 0.155 for Watch and 0.0257 for Standard.



* Four hubs behave unlike their tier label: Kolkata (Tier 1) is in Watch, Nagpur and Kochi (Tier 2) are in Escalate, and Dehradun (Tier 3) is in Watch. Playbooks should therefore follow the observed segment, and the tier label should be used only as a rough guide and reviewed regularly.



* The alert threshold is 0.5. On the test set, about 6.9 of every 10 flagged parcels are really delayed (precision 0.6889), and about 7.6 of every 10 delayed parcels are caught (recall 0.7561).



* Of the 48 new parcels, 8 were flagged, and 6 of those sit in Escalate-segment hubs and need a hub-manager escalation; the other 2 get a proactive customer call.



* I kept K = 3: the across-to-within ratio jumps from 2.894 at K = 2 to 5.3928 at K = 3, but rises only to 6.3047 (K = 4) and 6.8866 (K = 5), and those solutions contain clusters of fewer than 6 hubs (5 and 4 at K = 4; 4, 3 and 2 at K = 5), too small to carry their own playbook.

**(a) Production-readiness characteristics -> repository item** (at least five of seven)

|monitorability|new\_shipment\_actions.csv records probability, flag and action per parcel, and hub\_profile.csv, segment\_profile.csv and part\_c\_final\_test.csv give baselines to compare against|

**(b) Quantities to monitor, each with a numeric trigger** (at least three): Weekly delayed share of delivered parcels: the historical rate is 0.2317, so I would investigate if it moves more than 0.10 away for two consecutive weeks (sale weeks compared only with sale weeks).

**(c) Retraining schedule, sale window (15-28 Sept), and what drift looks like:** 1. Schedule. A sensible plan has three layers:



(b) fires

re-checking the hub segments and tier mismatches less often, because hub behaviour changes slowly







2\. The 15 to 28 September sale window. The model sees sale\_event\_flag, and it is one of the seven selected features (F-score 36.7281 in part\_c\_feature\_scores.csv), so the data contains a sale effect. The key point: compare a sale window with the previous sale window, not with ordinary weeks, because sale weeks are expected to have more delays and more flags. Judging them against normal weeks would trigger false alarms. 



I also found that sale-window parcels are delayed far more often (and Express most of all), which you can check in data/modelling\_table.csv. If you quote any such number, compute it yourself. The safest option is to describe it in words and cite only numbers from your outputs/ files.



3\. What drift looks like here:



Input drift: the mix of inputs changes, such as longer average distance\_km, more stops, more COD parcels, or more Express parcels. Compare against hub\_profile.csv.

Concept drift: the same inputs now lead to different delays, for example a hub that starts delaying more than before. That is how a hub would move from Watch to Escalate.

Data-quality drift: more missing values, more “Unknown” payment modes, or more 999 weight faults.

## Limitations

1. Small number of delayed parcels in the test set. The test set contains only 41 delayed parcels, so a single parcel shifts recall by about 0.024. Test recall (0.7561) is lower than validation recall (0.8333), but with so few positives I cannot tell whether that gap is real or chance; a larger or repeated evaluation would be needed before promising a recall level.
